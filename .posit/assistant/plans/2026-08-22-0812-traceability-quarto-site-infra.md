# Plan — Traceability backbone, pipeline DAG, and Quarto site infra

**Date:** 2026-08-22
**Goal:** Stand up the infrastructure that makes `cfb2nfl` faithful to and
transparent about its data — full lineage from raw → processed → model →
results and back — plus a `targets` pipeline, an auditable process map/DAG,
interactive-viz templates, and a well-structured Quarto website. Keep every
layer flexible now; lock choices in via the decision log as they prove out.

## Decisions locked for this pass (from clarifying Q&A)

- **Orchestration:** adopt `targets` **now** as the backbone (single source of
  truth for lineage and the process DAG).
- **Interactive viz:** **hybrid** — R htmlwidgets (`plotly`, `ggiraph`,
  `reactable`, `leaflet`) as the default; Observable JS reserved for a few
  bespoke explorables. `plotly` covers 3D.
- **Scope:** **full skeleton** across all seven items below (broad but shallow;
  each gets a working stub + clear TODOs, not a finished feature).
- **Reference docs:** `altdoc` (Quarto-native) to surface roxygen into the
  site — proposed default, recorded as a revisable decision.

## Guiding principles for the infra

1. **One DAG to rule lineage.** `targets` is the authoritative processing graph.
   The process map, "what's stale / what remains," and per-step audit all derive
   from it rather than being maintained by hand.
2. **Every transform is auditable.** A standard audit record captures, per step:
   input/output row & column counts, rows dropped, join-key coverage, NA counts,
   a schema hash, the governing data contract's pass/fail, timestamp, and git
   SHA. These accumulate into an audit log rendered on the site.
3. **Raw data is documented and immutable.** A data dictionary describes each raw
   source (endpoint, grain, columns, types, provenance). Processing never mutates
   raw files; it reads raw and writes new processed targets.
4. **Results trace back to inputs.** Model outputs carry the feature/version
   provenance needed to juxtapose predictions against the input data on the site.
5. **Flexible now, lock in later.** Modular functions, thin config, and ADRs for
   substantive choices. Prefer conventions that are easy to revise.

## Proposed repository layout (additions)

```
_targets.R                 # pipeline definition (stages below)
_quarto.yml                # website project (managed alongside altdoc)
R/
  ingest_*.R               # CFBD endpoint pulls (refactored from data-raw/DATASET.R)
  clean_*.R                # standardize schemas, coerce keys (athlete id -> string)
  link_*.R                 # athlete-id joins: picks <-> stats <-> roster <-> coaches
  features_*.R             # longitudinal change features (weight_delta, transfers, coach)
  audit.R                  # audit_step()/tar_audit helpers + schema hashing
  contracts_*.R            # pointblank agents per dataset (conference_tiers.R exists)
  viz.R                    # themed htmlwidget helpers (thematic-matched)
data-raw/                  # preserved as thin runners / exploration (kept, .Rbuildignore'd)
data/                      # raw + processed parquet (gitignored; release assets later)
inst/
  dict/                    # data dictionaries (one YAML per dataset)
site/ (or altdoc/ per tool convention)
  index.qmd                # landing
  about.qmd                # from VISION.md / README
  data/                    # dictionary + provenance/audit pages
  pipeline/                # process map / DAG page
  analysis/                # blog + analysis pages
  explore/                 # interactive-viz exemplars (2D / time-series / 3D)
  reference/               # roxygen reference (generated by altdoc)
tests/testthat/            # logic + data-contract tests
.github/workflows/
  format-check.yaml        # exists
  check.yaml               # NEW: testthat + pointblank contracts (PRs, pushes)
  site.yaml                # NEW: build + deploy Quarto site to GitHub Pages
  data-refresh.yaml        # NEW: scheduled CFBD refresh -> publish release asset
```

Exact site directory (`site/` vs altdoc's `altdoc/`+`docs/`) is finalized in
Phase 4 once altdoc's layout is confirmed; noted as a small open choice.

## Work plan (phased)

### Phase 0 — Groundwork & decisions (docs only)
- Add decision-log entries (copy `decisions/TEMPLATE.md`):
  - `0004` — Adopt `targets` orchestration + pipeline stage taxonomy.
  - `0005` — Lineage/audit design (audit record schema, data-dictionary format,
    contract-in-pipeline wiring).
  - `0006` — Quarto site architecture + `altdoc` for reference docs + viz stack
    (hybrid R/OJS).
- Update `.Rbuildignore` and `.gitignore` for new dirs (`_targets/` store,
  `docs/`/`_site/`, site sources as appropriate).

### Phase 1 — `targets` pipeline scaffold
- Refactor `data-raw/DATASET.R` ingestion into `R/ingest_*.R` functions (one per
  endpoint: picks, player-season stats, coaches, **roster by year (new,
  decision 0003)**, optional portal). Pure functions returning tibbles; writing
  handled by targets.
- Define `_targets.R` stages: **ingest → clean → link → features → model →
  report**, with the model/report stages present as placeholders wired to real
  upstreams.
- Wire existing `contract_conference_tiers()` in as a contract target; add
  contract stubs for picks/stats/roster/coaches.
- Confirm the graph builds with `tar_manifest()` / `tar_validate()` (read-only
  verification; no long network pulls required to validate structure).

### Phase 2 — Lineage / audit layer
- `R/audit.R`: `audit_step()` and a `tar_audit()` helper that, given named
  upstream/downstream targets, records the audit fields in principle #2 into a
  single accumulating audit tibble (a dedicated target).
- Schema-hash helper for schema-stability tracking across refreshes.
- `inst/dict/`: YAML data dictionaries for each raw + key processed dataset
  (endpoint, grain, key, per-column type/description/provenance).
- Wire pointblank agent results (`all_passed` + brief summary) into the audit
  record so contract status is visible per step.

### Phase 3 — Process map / DAG
- Pipeline page renders the live graph via `tar_mermaid()` (static, portable)
  with `tar_visnetwork()` as an optional interactive view, plus a hand-authored
  high-level mermaid overview aligned to the VISION ERD.
- Surface "what remains / what's stale" from `tar_outdated()` /
  `tar_progress()`.

### Phase 4 — Quarto website
- `_quarto.yml` website project; navbar sections: Home, About, Data
  (dictionary + provenance/audit), Pipeline (DAG), Analysis (blog + pages),
  Explore (interactive), Reference (roxygen via `altdoc`).
- Theme via `bslib`/brand; `execute: freeze: auto` for reproducible renders;
  qmd pages read pipeline outputs with `targets::tar_read()`.
- `altdoc` set up to generate the Reference section from roxygen.
- Content is stubbed: real prose short, structure complete.

### Phase 5 — Interactive-viz templates
- `R/viz.R`: themed htmlwidget helpers (thematic-matched to the site).
- Three exemplars in `explore/`: **2D** (feature vs draft outcome via
  `ggiraph`/`plotly`), **time-series** (`plotly` line of draft counts by
  season/position), **3D** (`plotly` scatter, e.g. height × weight ×
  production). Each pulls a pipeline target so input→viz lineage is explicit.
- One OJS exemplar noted as a follow-up placeholder (not fully built this pass).

### Phase 6 — Tests + contracts in CI
- `tests/testthat/` scaffold; `testthat::test_check` wired; port the implicit
  checks around `conference_tier_levels()`/`contract_conference_tiers()` into
  real tests; add data-contract test stubs.
- `.github/workflows/check.yaml`: `R CMD check`/`devtools::test()` + run data
  contracts on a small fixture (avoid full API pulls in CI).
- `.github/workflows/site.yaml`: build + deploy Quarto site to GitHub Pages on
  push to `main`.
- `.github/workflows/data-refresh.yaml`: scheduled CFBD refresh publishing
  parquet/DuckDB as a GitHub **release asset** (via `piggyback`), kept separate
  from the site build.

## Explicit non-goals for this pass

- No real modeling — model/report targets are wired placeholders only.
- No full CFBD re-ingestion run as part of this work (roster ingestion function
  is written; a full historical pull is a separate, network-bound step to run
  deliberately).
- Interactive pieces are exemplar templates, not finished analyses.
- CI workflows are authored but may need secrets/Pages settings enabled by you.

## Open choices to confirm during implementation

1. Site source dir: `site/` (plain Quarto) vs `altdoc/`+`docs/` (altdoc
   convention). Leaning altdoc convention to minimize custom glue.
2. Processed-data storage in CI: partitioned parquet vs single DuckDB file as the
   release asset. Leaning parquet first (simpler), DuckDB later if querychat/
   `orbital` needs it.
3. Whether to run `targets` inside CI or only build the site from committed
   release assets (leaning: site build reads release assets; pipeline runs
   locally / on the scheduled refresh job).

- `devtools::document()` + `devtools::check()` pass as a conventions gate.
- `quarto render` builds the site locally.
- Decision entries 0004–0006 committed; AGENTS.md/VISION.md updated where the
  infra materially changes what's described.
